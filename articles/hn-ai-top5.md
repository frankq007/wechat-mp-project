## 一、Claude 半小时找出 NIST 曲线 seed 的来源（710 分 / 276 评论）

先说结论：这不是漏洞，是一桩悬案的结案。

ECDSA 是使用最广的椭圆曲线密码标准，2000 年被 NIST 收进 FIPS 186-2。标准里每条曲线都带一个 seed 参数，用它的哈希值决定曲线系数 b。问题在于——这些 seed 是 NSA 给的，没有任何解释。比如 P-256 的 seed 是 `C49D3608 86E70493 6A6678E1 139D26B7 819F7E90`，没人知道它从哪来。

「参数是不是被故意选了带后门的」这个怀疑持续了二十多年，Koblitz 和 Menezes 还专门写过一篇《A Riddle Wrapped in an Enigma》讨论它。社区甚至为找到 seed 来源悬了赏。流传最广的说法来自 NSA 前雇员 Jerry Solinas 2015 年的回忆：seed 可能是某个搞笑口令的哈希，类似「给 Bob 和 Jerry 加薪」。Jerry 2023 年去世，线索断了。

Anthropic 的几个员工照着「搞笑口令哈希」这条线索去找，一无所获。2026 年 10 月，一位员工换了个问法：不给任何线索，直接问内部研究模型能不能自己搞明白 seed 是怎么生成的。

**半小时内，Claude 找出了 P-192、P-224、P-256、P-384、P-521 全部五条曲线 seed 的来源。**

答案很反高潮：根本不是任何哈希算法的输出，而是 C 标准库里 `lrand48` 这个随机数生成器的输出，种子就是一个 Unix 时间戳。算法是用时间戳 t 初始化 RNG，跑 n 轮迭代，每轮取 20 字节作为一个候选 seed——前 20 字节是候选 1，接着 20 字节是候选 2，以此类推。P-256 需要跑到第 1842 轮才吐出那个被写进标准的值。详情见 Anthropic 的官方说明：[Claude reveals ECDSA curve origins](https://www.anthropic.com/research/ecdsa-curve-origins)，Hacker News 讨论在[这里](https://news.ycombinator.com/item?id=50122800)。

![[ecdsa-seed-table.png]]
*图 2：Anthropic 给出的复现参数表。t 是 Unix 时间戳，n 是迭代轮数——P-256 要跑到第 1842 轮才吐出标准里那个 seed。*

Claude 的切入点是关键：它没去搜口令，而是**反推「生成这些曲线的那个软件必然长什么样」**——90 年代的 C 库自带的 PRNG 弱到输出可以被识别出来。

Anthropic 特意强调：这不是密码学攻击，也不构成 ECDSA 的弱点，反而让「曲线被做了手脚」的可能性大幅下降——因为生成方式简单到任何人都能复现。原话是「读者可以把它当作一个有趣的收尾章节，不需要采取任何行动」。

对做 AI 编程的人来说，可迁移的那一句是：**给 Agent 一个开放问题时，别急着把你的假设喂给它。** 人类被「搞笑口令」这个传闻带偏了很多年，而模型没有这个包袱。

## 二、Anthropic 公开 Claude Code 团队的代码评审流程（252 分 / 149 评论）

这是本周最值得抄作业的一篇，作者是 Addy Osmani 等三人，10 月 15 日发布：[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic)（[Hacker News 讨论](https://news.ycombinator.com/item?id=50122951)）。

背景数字：Claude Code 自己约 90% 的代码由 Claude 写；Anthropic 单仓每天落地的变更从今年 5 月的约 2500 个涨到 9 月的 30000 多个。从 6 月到 9 月，Claude Code 仓库合并的 PR 数量翻了一倍多，而**需要回滚的比例下降了 40% 以上**。

他们的核心转变是把问题从「有没有人读过这段代码」换成「这个变更可能出什么问题，哪一种检查（自动的还是人工的）最适合拦住它」。评审不再是路尽头的一道闸门，而更像你打字时的拼写检查——大多数变更在被人类看到之前，已经被 Claude 审过并修过至少一轮。

原文把流程分成七道关卡（配图里标的是「六层检查 + 底下的回滚」，因为最后一层回滚是托底而非拦截）：

**第 1 层：PR 之前先自证。** 给 Claude 一个它能真跑起来的东西——测试、构建，或者一张能跟设计稿对比的截图——然后要求它把输出贴出来，而不是说一句「我做完了」。之后由一个带全新上下文的子 Agent 复审 diff。Claude Code 的作者 Boris Cherny 认为，给模型一个验证自己工作的手段，可能是拿到好结果最重要的一件事，他估计这能让最终结果好 2 到 3 倍。

**第 2 层：每个 PR 都有 AI 评审。** 评审读的是 diff 相对整个仓库和 PR 声明意图的关系：这个改动解决了它要解决的问题吗？契合系统吗？会不会弄坏别的？改 bug 时它会去找根因。内部数据是：上线研究预览版后，拿到实质性评审意见的 PR 比例从 16% 涨到 54%。超过 1000 行的 PR 基本都会有发现，小 PR 大多干净通过。

发现项在给人看之前还要过一道关：多个 Agent 并行找 bug，另一组 Agent 对每条发现投票，票数够才发出来；纯风格、纯诊断、纯清理类的直接丢掉。留下的按严重度排序，打上 Important / Nit / Pre-existing 标签——「Pre-existing」这一项很讲究，它保证一个不是本次 PR 引入的老 bug 不会算到作者头上。每条发现都必须回应：要么修，要么写明理由关闭。

**第 3 层：能阻塞合并的安全评审。** bug 评审或安全评审只要还有未关闭的发现项，PR 就不能合。

**第 4 层：常规自动化检查。** lint、类型检查、各平台测试、构建。一个典型的 CLI PR 在有人看之前要跑几十项检查。PR 模板会问「这个改动怎么测的」和「怎么撤销」——Claude 可以填，但要由发起这个改动的人签字。

**第 5 层：人工审批按风险分级。**

| 风险 | 例子 | 需要几个人工审批 |
|---|---|---|
| 低 | 文档、文案、内部功能、开关后的增量改动 | 自动评审和安全检查全绿后，0 人 |
| 中 | 常规产品改动，以及缓存、自动更新器、系统提示词等敏感区域 | 1 人 |
| 高 | 最高风险代码，外加一小撮永远需要两人的路径 | 2 人 |

分级由分类器读变更内容决定，**看的是改动本身，不是作者是谁**。另有三条硬规则值得注意：Agent 的批准永远不算一个人的批准；只有在仓库信任名单里的作者才走轻量路径；一次批准只覆盖一个具体 commit，之后有新的 commit（比如 Agent 推的、或人工手解的合并）就得重新批。

还有一条责任规则：「谁发起的谁负责」。Agent 写的 PR，指挥 Agent 的那个人就算作必需评审人之一，跟你自己敲的代码同等对待。

**第 6 层：合并队列 + 开关 + 灰度。** 合并队列会把变更应用到 main 之后重跑所有检查，避免两个各自通过的 PR 合出一个坏 main。新行为通常先带开关推给 Anthropic 员工。

**第 7 层：快速发现、快速回滚。** 开关可以不发版就关掉，Claude Code 有每周轮值的 on-call，事故复盘要回答「本该是哪一层拦住它」。

**七层之外：机器读了代码，人还怎么学代码？** 原文还回答了另一个问题。团队的做法是问 Claude 要「正好那一块」的解释：Claude 写一份 explainer，几分钟生成、反映代码当下的状态；有人更进一步，让 Claude 针对那块代码生成一个小可视化产物，按这个人习惯的方式教他。原文的说法很扎心：逐行读琐碎 diff 几乎教不会你任何东西，一份「你正要改的那个模块」的 explainer 才教得多。

### 踩过的坑：评审必须收敛

这一段是全篇最实在的部分。

Agent 作者加 Agent 评审可以互相耗到天荒地老。他们有一个 CLI PR 在夜里来回跑了**五十多轮**评审和修复，最后是作者手动叫停的。

于是他们去做了 git blame，结果发现：评审器反复标记的东西里，约 **59% 是它第一轮之前就存在的老代码**。也就是说它很少在发现新 bug，只是每轮多挖出几个旧 bug。而团队自己也有责任——因为「每轮都能抓到点东西」，大家习惯了默认跑好几轮。

修复手段有四条，全都可以直接抄：

1. **设轮次上限**：三轮之后，评审器不再挑细节，而是要求作者退一步重新考虑方案。
2. **前几轮之后只审 diff**，不再全仓扫。
3. **标记 bug 的类别而不是单行**，让作者一次改掉所有同类实例。
4. **不重复已发布过的发现项**。

他们还发现噪声成本在 Agent 作者身上会被放大：人可以几秒钟挥掉一条 nit，Agent 会真的去修，于是多一个 commit、多一轮评审。团队现在把「通过所需轮数」和召回率放在一起追踪，写下来的优先级是：先抓真 bug，其次才是减少评审轮数。

另外，任何事故现在都会变成一个 eval——团队收集了过去导致事故的 PR 及其修复和回滚，由熟悉那段代码的工程师逐个确认 bug 和位置，评审器每天对着这套集合跑一遍。

## 三、苹果：4 台 Mac Studio 跑 816B 参数的 Muse Spark Open（273 分 / 57 评论）

苹果机器学习研究团队 10 月 15 日的文章，配合当天发布的新版 MLX：[Local and Distributed Large LLM Inference with MLX and RDMA on Mac Studio](https://machinelearning.apple.com/research/mlx-distributed-inference)。

要点：Muse Spark Open 是一个 816B 总参数、42B 激活参数的 MoE 模型，以 NVFP4 精度评测。在 4 台 M5 Ultra Mac Studio 组成的集群上，8192 token 上下文下解码速度超过 **36 tokens/s**——高于人类平均阅读速度。单机 Mac Studio 最高可配 512GB 统一内存，跨机靠的是 **RDMA over Thunderbolt** 驱动，文章对比了 2 机流水线并行、2 机和 4 机张量并行三种方案。

同场对比的还有 Mistral Medium 3.5（128B，FP8）和 Qwen 3.8（27B，BF16）。M5 这一代的 GPU Neural Accelerator 提供专用矩阵乘法单元，是速度提升的硬件基础。

对开发者来说值得关注的不是「苹果又跑分」，而是**本地推理的规模边界在被统一内存 + 高速互联往外推**：万亿参数级别的开放权重模型，已经进入了「桌面上能跑」的讨论范围，MLX 本身是开源的。

## 四、PS5LM：把越狱 PS5 变成家里的私有模型服务器（215 分 / 57 评论）

GitHub 项目 [cobanov/PS5LM](https://github.com/cobanov/PS5LM)，GPL-3.0，截稿时 375 star、68 fork。

一句话概括：在越狱 PS5 上用 llama.cpp 的 Vulkan 后端跑 GGUF 模型，主机 RDNA 2 GPU，划出 11.4GB 共享内存给模型和上下文，然后通过网络把服务提供给全屋设备——运行时不需要 PC、不需要云、不需要账号。

对做 AI 编程的人最有用的一点是它暴露的接口：OpenAI 的 `/v1/chat/completions` 和 Anthropic 的 `/v1/messages`，**Claude Code 可以直接连上去用**。它还有一个给电视看的界面：首页显示模型和实时速度、请求流，另有 Models、Console（温度/功耗/负载曲线）、API、Settings 几个页面。最新版还接入了 Ollaya 的决策模型（d1、Clef、OpenJev 等），走同一个 `/v1/systemone` API，返回带校准概率的结构化决策。

它当然不是性能怪兽，README 里的演示是 Qwen 3.5 9B。但它代表了一类很有意思的方向：**家里已经通电联网、GPU 长期闲置的那台设备，能不能直接当推理节点用。**

## 五、90% 的美国工时，花在 AI 评测几乎没覆盖的任务上（418 分 / 353 评论）

Mercor Research 做的 [Benchmark Map](https://www.mercor.com/research/labor-index/benchmark-map/)，把现有 AI 评测基准映射到美国劳工部 O*NET 职业分类上，覆盖 924 个 benchmark。

数字很难看：O*NET 的 923 个职业里，只有 208 个职业存在「至少被 5 条评测提示覆盖」的任务；22 个职业大类里有 6 个大类一个这样的职业都没有。按工时算，**约 90% 的美国工时花在了现有评测覆盖极少或完全没有的任务上**。

而且覆盖不是随机的：回归分析显示，评测覆盖概率跟该职业的「AI 暴露度」标签和年薪总额正相关——也就是说 AI 社区在优先盯着最大的劳动力市场做评测。医疗健康类 89 个职业只有 12 个被覆盖，教育类 62 个里只有 9 个。

![[mercor-coverage.png]]
*图 4：按覆盖率算计算机与数学最高（29/36），但绝对数量上商业与金融更多；医疗、教育、管理这几个大类覆盖最薄。*

这条对日常写代码的人的意义是：**榜单分数和你手上真实工作之间的距离，比想象中远得多。** 选模型时，自己那套私有 eval 的价值又被抬高了一格——这也正好呼应上面第二条里 Anthropic 的做法：把每次事故沉淀成 eval，比追榜单可靠。

## 另外两条值得一提

- **Home Assistant 的密钥泄露检查被用户要求改成 opt-in**（202 分 / 155 评论）。一位用户在 2026.10.1 上开了 [issue](https://github.com/home-assistant/home-assistant.io/issues/49314)：系统会把他的密码拿去跟泄露密码库（pwned-passwords）比对，而他从未授权过这件事——「即使传的是哈希也不行」。他的诉求很直接：这类机制应该是默认关闭、用户主动开启，并且要能关掉。它不是第三方插件而是官方内置行为，这才是讨论热度高的原因：**默认值就是一种授权**。做工具链、做 MCP 集成的人可以把这条当成一次免费的用户预期调研。
- **[/dev/null](https://dev-null.sh)：给开发者的社交网络**（135 分 / 120 评论）。一个极简发帖流：GitHub 账号登录，Trending / Following / Latest 三个入口，帖子上只有赞、引用和回复。本周 Laravel 作者 Taylor Otwell、nunomaduro 都在上面发了帖，还有人发帖喊「他们居然在用手机发版」。帖子的互动只有赞、引用和回复三个动作，界面干净到有点复古。HN 评论区 120 条在争的也是同一件事：开发者到底还需不需要又一个社交网络。

## 一条主线

把这 5 条摆在一起，本周的信号很清楚：AI 编程的重心正在从「让模型写出代码」移到「**让模型能验证自己写的代码**」。

Anthropic 那篇文章里最狠的一句话，是 Boris Cherny 说的：给 Claude 一个验证工作的手段，可能是拿到好结果最重要的一件事。ECDSA 那条也是同一个逻辑——Claude 能破案，靠的是它可以真的去跑 `lrand48` 复现 seed，而不是靠语言上的猜测。

如果你只打算从这周的热榜里带走一件事，我建议是这个：**先给你的 Agent 一双能看见结果的眼睛，再谈让它多干活。**
